# Как вносить правки

## Порядок работы

Добавить своё может любой. Способ зависит от того, есть ли у тебя право записи в репозиторий.

### Без права записи: fork и pull request

Это путь по умолчанию для всех студентов.

1. Нажать **Fork** на странице репозитория — появится твоя копия `github.com/<твой-логин>/360`.
2. Склонировать её и внести правки:

   ```sh
   git clone git@github.com:<твой-логин>/360.git
   cd 360
   git switch -c web/lesson-07          # ветка: <предмет>/<что делаем>
   # ... правки ...
   git add -A && git commit -m "web: lesson 7, формы"
   git push -u origin web/lesson-07
   ```

3. Открыть pull request из своей ветки в `x60team/360`, ветка `main`. GitHub предложит это сам после push.

Одна ветка — один конспект или одна работа. Чтобы подтянуть в свой fork свежие изменения, на его странице есть кнопка **Sync fork**.

### С правом записи: прямой push в `main`

Отдельная ветка и pull request не обязательны.

```sh
git pull --rebase                       # забрать чужие изменения перед отправкой
git add -A && git commit -m "web: lesson 7, формы"
git push
```

`--rebase` нужен обязательно: история `main` линейная, push с merge-коммитом GitHub отклонит. Force push в `main` запрещён.

Отдельных долгих веток под предметы не заводим, предметы разделены папками.

## Сообщения коммитов

Формат: `<предмет>: <что сделано>`.

```
programm_modules: конспект лекции 3, ветвление в git
mobile: lunch tray, навигация
testing: pytest_2, фикстуры
docs: поправил ссылки в README
```

## Конспекты

- Лежат в `<предмет>/notes/`, формат — Markdown, один файл на тему.
- Имя файла начинается с номера, чтобы темы шли по порядку: `01-жизненный-цикл-по.md`.
- Картинки кладём в `<предмет>/notes/assets/` и перед коммитом сжимаем.
- Ссылки между конспектами — относительные.

## Практические работы

- Небольшая работа — папка внутри `<предмет>/practice/`, например `web/practice/lesson-07/`.
- Крупный проект (Unity, Android) — отдельный репозиторий в организации, а в `README.md` предмета добавляем на него ссылку.
- В корне работы желателен короткий `README.md`: что за задание и как запустить.

## Чего в репозитории быть не должно

Репозиторий публичный, а история git хранит всё навсегда.

- **Большие бинарные файлы**: презентации, сканы, видео, сборки (`.apk`, билды Unity). Их кладём на облачный диск или в Releases, в репозитории оставляем ссылку.
- **Результаты сборки и зависимости**: `build/`, `node_modules/`, `Library/`, `.venv/`. Они уже перечислены в `.gitignore`.
- **Именные отчёты и персональные данные**: отчёты с ФИО, номера зачёток, контакты.
- **Чужие материалы**: слайды преподавателей, сканы учебников, файлы курсов — только с разрешения автора.
- **Пароли, ключи, токены**.

Отчёт в `.docx` стоит переписать в Markdown: его можно читать на GitHub и видно, что изменилось.
